# Simular ciclo de cobro rápido (QA) — hechos verificados 2026-07-24

Advisory para Pedro: "¿periodo de 2 días?" — NO existe periodicidad nativa < semanal; la palanca real es fechas manuales + settings comprimidos + correr los crons a mano.

- **Periodicidades nativas** (`Periodicity` central, `CentralCatalogModel`): MONTHLY, BIMONTHLY, YEARLY, EVENTUAL, WEEKLY, BIWEEKLY. Resolver `PeriodicityScheduleResolver` solo materializa esas 5 automáticas (match sobre UUID; default → []). Mínimo automático = WEEKLY (Lun–Dom). UI (`PeriodicitySelector.tsx`) oculta BIWEEKLY/BIMONTHLY (`hidden: true`); visibles: Mensual, Semanal, Anual, Eventual.
- **Fechas libres**: `ChargeBatchCreateRequest` y `ChargePolicyCreateRequest` validan `issued_at`/`due_date` solo como `date` + `after_or_equal:issued_at` — se permiten fechas PASADAS (backdating OK, sin guard "future"). Para política DIRECT (EVENTUAL) `issued_at`/`due_date` son REQUIRED; `valid_from/to` PROHIBITED.
- **Comandos sin opciones**: `collections:refresh-statuses` y `collections:generate-monthly` NO aceptan `--tenant` ni `--date` — iteran `Tenant::all()` + `$tenant->run()` y usan `Carbon::today()` (timezone de la app, no del tenant). `collections:send-reminders` a 07:00. Schedule en `CollectionsServiceProvider::registerCommandSchedules()`: 01:00 / 06:00 / 07:00.
- **OVERDUE es estrictamente después**: `$today->isAfter($dueDate + graceDays)` (ChargeStatusService::resolveStatusKey ~322). Con grace=0 y due_date=hoy → overdue MAÑANA. DUE_SOON solo si `paid == 0`.
- **Recargo requiere policy**: `computeSurcharge` retorna 0 si `charge_policy_id === null` → cargos directos (DirectChargeService, grace 0 explícito) NUNCA acumulan recargo. Regla `from_month=1` dispara el día 1 de mora (monthsOverdue 1-indexed). Recargo es derivado/idempotente, se recalcula en el mismo cron 01:00 (accrueSurcharge antes de recomputeCharge, misma tx por cargo).
- **Settings aceptan 0**: `ConfigurationController` — `due_soon_days` min:0 max:60, `grace_days` min:0 max:60, `charge_generation_day` min:1 max:28. Resolución RESOLVE-AT-FSM-TIME (snapshot per-charge gana si no es null).
- **Statement cache**: `StatementTotalsCacheObserver` (en Charge + CreditBalance, `ShouldHandleEventsAfterCommit`) invalida solo — el cron de statuses/recargos ya dispara `saved()`; NO hay que limpiar cache a mano.
- **Batch idempotente**: unique parcial (tenant, policy, year, month, COALESCE(cycle,-1)) WHERE month IS NOT NULL — correr generate-monthly N veces el mismo día no duplica.
- Receta rápida completa: batch eventual con due_date=ayer + grace 0 en policy + `php artisan collections:refresh-statuses` a mano = overdue + recargo en segundos, sin esperar días.

Verificado: ancla 2026-07-01 (20635 días, impar) → `[2026-06-30, 2026-07-01]` cruzando el mes; ancla 2026-07-24 (20658, par) → `[24/07, 25/07]`. `computeLifecycleMilestones` se corrigió solo (deriva de periodBounds). **Regla general: cualquier periodicidad NUEVA hay que agregarla EXPLÍCITAMENTE a `periodBounds` — el fallback mensual no falla, miente.**

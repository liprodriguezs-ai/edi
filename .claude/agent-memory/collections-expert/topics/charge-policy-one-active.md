# Charge policy "one active per concept+periodicity" block — investigated 2026-07-03 (NO code changed)

User complaint: creating a 2nd charge_policy for a concept that already has one is BLOCKED, feels arbitrary. Verdict: DELIBERATE (prevents real double-billing), but the guard is coarser than the actual risk.

- **Exact block, 2 layers**: (1) request-level `ChargePolicyCreateRequest.php:90-96` — `Rule::unique('charge_policy')->where('tenant_id',...)->where('charge_concept_id',...)->where('is_active',true)->whereNull('deleted_at')` on `periodicity_id`, ONLY when the new policy would be active (`$this->boolean('is_active', true)`); message `periodicity_id.unique` = "Ya existe una política activa para este concepto y periodicidad." (`:109`). (2) DB partial unique index `charge_policy_active_unique` on `(tenant_id, charge_concept_id, periodicity_id) WHERE deleted_at IS NULL AND is_active = true` (`create_charge_policy_table.php:57-61`) — the race backstop.
- **Relation IS 1:N** (not 1:1): `ChargePolicy.charge_concept_id` plain FK; `ChargeConcept::policies()` `hasMany`; FE `ChargePolicyListPage.tsx:50-52` says "relación 1:N", list + "Nueva programación" always enabled. So multiple policies per concept ARE supported — just not two ACTIVE ones with the SAME periodicity.
- **What breaks with 2 active same-concept+same-periodicity**: `GenerateMonthlyChargesCommand::activePoliciesFor()` (`:166-179`) filters by periodicity_id + is_active + window, NOT by concept → returns BOTH, clones+activates a batch from EACH. `ChargeGenerationService::activateBatch()` idempotency (`:90-93`) is scoped ONLY by `charge_batch_id` — NO dedup by `(unit_id, charge_concept_id, period)` across batches. A unit in BOTH target sets gets TWO `charge` rows for the SAME concept+period → real double-billing. No overlap/disjoint-target detection exists anywhere.
- **Verdict**: deliberate core intent, but stricter than needed — forecloses tiered pricing for the SAME concept+cadence across DISJOINT targets (e.g. Mantenimiento mensual at one amount for `by_type=casa`, another for `by_type=depto`). Workaround: model each tier as its OWN `charge_concept`, OR use `BY_SHARE`/one blended formula. Lifting the constraint outright would remove the ONLY safety net — NOT safe without adding target-overlap validation first.
- **Proper relaxation design**: keep the unique index but allow >1 active per (concept, periodicity) ONLY when resolved unit sets are provably disjoint at creation time (compute `TargetResolver::resolve()` for new vs every active sibling, reject on intersecting unit id). Needs app-level check inside `ChargePolicyService::create/update` tx with row lock on siblings; same check on REACTIVATION and target edits; `activePoliciesFor` stays unchanged.
- **Adjacent gap**: `ChargePolicyUpdateRequest.php` has NO re-check of the partial-unique tuple when REACTIVATING (`is_active:true`) or changing `periodicity_id` on an active policy (only `validateAutomaticPeriodicity`/`validatePeriodicWindow` run). A collision hits the DB constraint directly, and there is NO global `QueryException`→422 mapping (`bootstrap/app.php:64-66`) → likely a raw 500, not a clean 422. Flag if reactivation-after-deactivate becomes a supported workflow.
- **User workaround TODAY (no code change)**: deactivate the existing rule (toggle "Activa" off, save — partial index counts only is_active=true), THEN create the new one. For different amounts per segment, split into separate `charge_concept` rows.

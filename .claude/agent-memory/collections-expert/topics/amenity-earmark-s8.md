# AmenityReservations S8 earmark — REVIEWED 2026-07-06 (branch feat/amenity-reservations, uncommitted)

First consumer of the earmark subsystem after Projects. Design matches on D1/D2/deposit/guards/tenant-scope/reversal; one HIGH money-correctness bug in the reversal path.

## Shape
- deposit=ANTICIPO settled: outstanding=cost_amount ONLY (migration comment correct at `amenity_reservation_table.php:61`); deposit only enforces the first-payment minimum.
- Handler `AmenityReservationEarmarkHandler` (EARMARK_TYPE='amenity_reservation'). Charge factory `AmenityChargeService::createChargeForReservation` (shared concept code `AMENITY_RESERVATION`, category `idOfKey(KEY_SERVICES)`, charge_policy_id/charge_batch_id null, grace 0, due_date=today). Observer `AmenityReservationChargeApplicationObserver` (created / updated[applied_amount only] / deleted → `ReservationService::syncFromChargeApplication(reservationId)` RECOMPUTE-FROM-SUM, not delta). Charge link migration `2026_07_06_100008_add_amenity_reservation_id_to_charge_table.php` (nullOnDelete, indexed).
- `ReservationStatus` (central, fixed UUIDs, `ReservationStatus.php`): PENDING_APPROVAL / PENDING_PAYMENT / CONFIRMED / CANCELLED / REJECTED / COMPLETED / NO_SHOW. Payable set (handler) = {PENDING_PAYMENT, CONFIRMED}. ACTIVE_STATUSES (cancellable / sync-mutable) = {PENDING_APPROVAL, PENDING_PAYMENT, CONFIRMED}. Amenity snapshots cost_amount/deposit_amount/amount_outstanding (TenantMoneyCast, bigInteger) + balance_due_date(date)/payment_deadline(timestamp). `Amenity.bank_account_id` = required earmark destination (handler enforces equality).
- Reservation cancel route custom (`POST /amenity_reservation/{id}/cancel`, NOT Orion-wrapped) → `ReservationService` owns tx; `reverseConfirmedEarmarkPayments` (`ReservationService.php:276-283`) loops CONFIRMED earmark payments → `PaymentService::cancel` (nested = SAVEPOINT), BEFORE the flip to CANCELLED.
- FSM edges in `syncFromChargeApplication` (`ReservationService.php:310-347`): outstanding==0 → CONFIRMED + clear balance_due_date; PENDING_PAYMENT & settled≥deposit → CONFIRMED + fresh balance_due_date; CONFIRMED & settled==0 → revert PENDING_PAYMENT; terminal untouched (ACTIVE_STATUSES guard `:314`).

## HIGH BUG — FIXED 2026-07-10 (verified)
The reversal-leaves-charge-open bug is now RESOLVED, but NOT in PaymentService: the fix lives in `AmenityReservationChargeApplicationObserver::deleted()` (`:59-77`). When a PaymentApplication on an `amenity_reservation_id` charge is deleted (payment cancel path), the observer sets `charge.is_cancelled=true` + `cancellation_reason='Reservation earmark payment reversed'` BEFORE calling `syncFromChargeApplication` (condition: `!is_cancelled && paid < expected`; paid was already zeroed by PaymentService's `adjustChargePaidAmount(-applied)` which runs before `->delete()`). So the charge leaves both `openChargesFor` (FIFO) and the `settledRaw` filter — no FIFO magnet, no cron aging, no worst-wins pollution. `PaymentService::cancel` itself STILL never touches the charge (unchanged) — the consumer's observer owns the cancellation, exactly the placement the SDD note recommended. Projects has NO equivalent observer cancel, so the same-shape bug likely still LIVES for project contributions (their charge re-opens on reversal). ORIGINAL (now-historical) description:
Reversing an earmark payment left the amenity charge `is_cancelled=false` — `PaymentService::cancel` deletes the application + zeroes paid_amount but never cancels the charge. The re-opened charge (expected>0, paid0, amenity_reservation_id set, due_date=creation day=past):
1. re-enters `openChargesFor` (`PaymentService.php:786-794`) and sorts to the FRONT of FIFO → the next unrelated maintenance payment is diverted into a dead reservation charge (violates D1 "never a FIFO magnet");
2. that stray application re-fires the observer → `settledRaw` sum (`ReservationService.php:319-323`, filter `is_cancelled=false`) drops outstanding → wrongly advances reservation PENDING_PAYMENT→CONFIRMED from unrelated money (LIVE in the payment-cancel path where the reservation reverts to PENDING_PAYMENT/ACTIVE; reservation-cancel path is terminal so the ACTIVE_STATUSES guard protects the FSM but the money is still absorbed);
3. re-enters cron `refreshAllOpenCharges` (`ChargeStatusService.php:175-183`, `is_cancelled=false`) → ages to OVERDUE → pollutes unit worst-wins + /delinquency.

FIX (now applied, see above): on reversal mark the amenity charge `is_cancelled=true` — done in the observer deleted hook.

## MONEY-FLOW FOOTGUNS — found 2026-07-10 (deep money audit, AUDIT-ONLY, uncommitted branch)
Domain-logic footguns in the resident-facing amenity money flow (not accounting corruption — the ledger holds — but stuck-states, dead config, and slot-squatting a Mexican-fraccionamiento treasurer would reject):
1. **Resident self-submits CASH with no comprobante** (`SubmitReservationPaymentSheet.tsx:161` requires comprobante only for non-cash; CASH is the default `:51`). Creates a PENDING_VALIDATION payment with zero proof → trips `payment_one_pending_per_earmark` → blocks any further payment. Residents hold `create.payment_submission` but NOT `update.payment` (RolePermissionTableSeeder `:570` grants submission; cancel/reject at `PaymentController:283,303` need update.payment) → NO resident path to withdraw it. Cash in a cluster is physically handed to the admin and registered via `payment/register` (born CONFIRMED) — resident self-declaring cash is domain-nonsense. FIX: block CASH on resident submit (non-cash only) + give the submitter a withdraw path for their own PENDING_VALIDATION payment.
2. **`canPay`/`canRegisterPayment` ignore the one-pending guard** (`MyReservationsPage.tsx:47`, `AmenityReservationDetailPage.tsx:220` gate only on payable-status + outstanding>0). "Pagar"/"Registrar pago" stays shown while a PENDING_VALIDATION earmark payment exists → clicking walks into the submit-time 422; resident can't clear it. FIX: reflect pending-earmark-payment state in the gate.
3. **`payment_timing` (pay_upfront/pay_later) is DEAD** — stored on Amenity, validated (`AmenityCreateRequest:56`), shown, but read by ZERO domain logic (grep: no reads in ReservationService/Handler/frontend gating; FE schema.ts:91 even comments it "only means something when has_cost"). An admin picking "pagar por adelantado" gets identical behavior to "pagar después". FIX: implement (pay_upfront ⇒ confirm only at outstanding==0) or remove the field.
4. **No-deposit costed amenity confirms on ANY token partial** — `syncFromChargeApplication` (`ReservationService.php:775-786`) PENDING_PAYMENT→CONFIRMED branch uses `settledRaw >= depositRaw`; a `has_cost + requires_deposit=false` reservation snapshots deposit_amount=null → depositRaw=0 → a $1 payment on a $150 amenity flips it CONFIRMED (holds_slot locked) leaving $149 outstanding until silent expiry. validateSubmission's min gate (`Handler:86`) also skipped (depositRaw=0). Slot-squatting vector + misleading "CONFIRMED". FIX: gate the deposit-confirm branch on `depositRaw > 0`; no deposit ⇒ confirm only at outstanding==0 (natural home for pay_upfront #3).
5. **Orphaned PENDING_VALIDATION payment on reservation cancel/expire** — `reverseConfirmedEarmarkPayments` (`ReservationService.php:707-714`) filters `PaymentStatus::CONFIRMED` only; a PENDING_VALIDATION earmark payment survives its reservation going terminal. It can never be validated (handler `assertPayable` rejects terminal → 422 forever) and residents can't cancel it — only a tesorero `reject` clears it. FIX: on cancel/expire also reject any PENDING_VALIDATION earmark payment for the reservation.
6. **(cross-cutting smell)** refund of a confirmed CASH amenity payment is a bare `decrementBankBalance` (`PaymentService.php:935`) — no Expense/egreso row, only `cancellation_reason`. Consistent across all Collections cancels, not amenity-specific.
CORRECT (verified fine, do NOT re-flag): surcharge charge omits `amenity_reservation_id` (`AmenitySurchargeService:79-89`) → stays OUT of amount_outstanding, IN the unit statement/FIFO, no double-count. Deposit-then-balance second payment settles correctly. Terminal-freeze of amount_outstanding is cosmetic (status-gated in UI).

Two reusable checks for any Kivo7 module that (a) seeds role permissions AND (b) gates a "resident self-service" endpoint by excluding staff, or (c) exposes a lightweight count/widget endpoint. Both are FINAL-STATE issues invisible per-slice (permission seeder and controller live in different slices).

**1. Staff-exclusion gates key on `create.{entity}` → board roles must NOT get create/update on an operational entity unless you WANT them treated as staff.**
Pattern in this repo: resident self-service endpoints (e.g. `PackageController::myPackages`, `VisitorController` scoping) treat a token holding `create.{entity}` as "staff" and 403 / unscope them. In Mexican clusters the board (president/treasurer/secretary/vocal/oversight) are THEMSELVES residents. If the role seeder grants a board role `create.{entity}` (for "oversight"), that role is silently excluded from the resident QR/self-service view — a certain (not hypothetical) UX regression for a whole role.
- Package final review: president was granted `read,create,update,report` on `package` (seeder comment "full package oversight (read/approve/report)"), while treasurer/oversight correctly got only `read,report`. The design (ADR-1) said president = read + read/report.report_package, NO mutation. The create.package grant makes EVERY president 403 on `/my-packages` and lets them mutate custody (verify/handover/return/incident/reassign) beyond design.
**How to apply:** when a role seeder grants `create`/`update` on an operational entity, grep controllers for `tokenCan('create.{entity}')` used as a staff marker. If found, board-read-only roles getting create/update is almost always an over-grant — cross-check against the design's permission table. WARNING (not CRITICAL: board is trusted, and they can still retrieve via the staff index which reveals their own unit's code).

**2. Count/widget endpoints authorized by `read.{entity}` (which residents hold) leak cluster-wide aggregates.**
A module's detailed report is correctly gated to `read.report_{entity}` (board/admin only), but a sibling lightweight count endpoint for a dashboard widget is gated to `read.{entity}` so guards (who hold `read.{entity}` but NOT `read.report_{entity}`) can load it. Residents ALSO hold `read.{entity}`, so they get unscoped cluster-wide counts while their package LIST is unit-scoped — a scoping inconsistency + low-sensitivity info exposure.
- Package final review: `PackageReportController::pendingCount` authorizes `read.package` and returns `{total, d7_plus}` across ALL units; `aging`/`export` correctly use `read.report_package`. Guards need pendingCount but have only `read.package` (security role lacks `read.report_package`).
**Fix shape:** gate the widget on `create.{entity} || read.report_{entity}` (mirrors `scopeToResidentUnitsIfNeeded`) so guards+board see it but residents don't. WARNING (counts only, no PII).

**Confirmed GOOD in this review (do NOT re-flag):** custom-action authz present on ALL routes (verify-code/handover/return/incident/reassign→`update.package`, batch→`create.package`, myPackages→`read.package`+staff-exclusion, reports→`read.report_package`/`read.package`); `TraitController::authorize` throws 403 on missing `tokenCan`. Tenant isolation solid: `Setting` IS `BelongsToTenant` (per-tenant pickup policies, no global leak); `verifyPickupCode`/`handover`/`reassignUnit` all tenant-scoped via `BelongsToTenant`; routes resolve `{packageId}` inside the method (after initializeTenancy) not via implicit binding. `module_system.csv` covers all 5 new module rows; empty group/icon on hidden catalogs matches the existing convention. `upsertCatalog` derives update columns per-call so the `package_status` seed (name/key/color, no order/is_active) does not break. pickup_code partial-unique `(tenant_id, pickup_code) WHERE deleted_at IS NULL` + bounded gen loop + 23505 savepoint-retry is correct.

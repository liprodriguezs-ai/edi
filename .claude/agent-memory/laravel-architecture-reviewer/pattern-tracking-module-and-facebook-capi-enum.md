**Context**: `backend/Modules/Tracking/**` (created 2026-07-01) is a brand-new headless module — marketing conversion tracking (Facebook Conversions API + GA4 Measurement Protocol), no UI/CRUD/sidebar, no tenant scoping (central table, tracking can happen before a tenant exists).

**1. Architecture mirrors `App\Notifications\Services\NotificationDispatcher` almost exactly** — confirmed GOOD, use as the reference precedent for any future "fan out to N external channels via a queued job" module:
- `TrackingChannelInterface::send(TrackingEvent $event): void` ↔ `NotificationChannelInterface::send(array $recipients, ...)` — single-method, ISP-compliant.
- `TrackingDispatcher` (CHANNEL_MAP + `dispatch()` + public `makeChannel()` resolved through the container so test spies still apply) ↔ `NotificationDispatcher`.
- `DeliverTrackingEventJob` (dumb sender, `tries=3`, `backoff()` escalating, `failed()` → `report()`) ↔ `DeliverChannelMessageJob`. One job per (channel × event) so one channel's outage never blocks another and a retry never double-sends to a channel that already succeeded.
- Every channel no-ops with `Log::warning` when its config credentials are absent (same convention as `SmsChannel`), and lets transport errors PROPAGATE (`Http::...->throw()`) so the job actually retries.
- New precedent established here (not seen before at module level): a per-module `app/Contracts/` + `app/DTO/` folder pair. Clean, ISP/DIP-correct, worth reusing verbatim for the next polymorphic-channel module instead of re-deriving the shape.
- `TrackingEvent` model correctly uses `CentralConnection` (Stancl) + `BaseModel::columns($table, false)` (no `tenant_id`) since events can fire pre-tenant (anonymous visitor, mid-registration). `CentralConnection` IS an established pattern in this repo (User, Role, Country, SubscriptionPlan, TenantEntitlement, etc. all use it) and there IS a `central` connection configured in `config/database.php` — do NOT flag `CentralConnection` usage as suspicious by itself, verify against `config/database.php` first.

**2. Concrete external-API gotcha (CRITICAL when found): Facebook Conversions API `action_source` field has exactly 7 valid enum values** — `email`, `website`, `phone_call`, `chat`, `physical_store`, `system_generated`, `other`. **There is no plain `"system"` value.** Verified 2026-07-01 via Meta's Conversions API parameters docs (developers.facebook.com/docs/marketing-api/conversions-api/parameters).
- Found in this review: `Modules\Tracking\DTO\TrackingEvent` is fine (default `'website'`), but every server-side hook that sends a system-generated conversion hardcodes `'action_source' => 'system'` — `StripeWebhookListener::dispatchPurchaseTracking()`, `AuthController::dispatchRegistrationTracking()` (both CompleteRegistration and StartTrial). `TrackEventRequest`'s validation whitelist (`'action_source' => ['nullable','string','in:website,system']`) even enshrines the wrong value.
- Impact if real: `FacebookConversionsChannel::send()` sends this raw (no translation table, unlike event names which DO have `GA4_EVENT_NAME_MAP`) straight to the Graph API. If Meta rejects the invalid enum, `Http::asJson()->throw()` turns it into an exception → `DeliverTrackingEventJob` retries 3× then fails silently (only visible via `report()`/logs) → **100% of server-side Facebook conversions (the highest-value ones: Purchase, CompleteRegistration, StartTrial) never land**, while the browser-side pixel keeps working, masking the breakage.
- **How to apply**: any time a module talks to a named third-party marketing/ads API (Meta CAPI, GA4 MP, TikTok Events API, etc.), verify enum-shaped string fields (`action_source`, event names, currency codes) against that API's actual published enum — do NOT trust an internal convention string like `'system'` that "sounds right" without checking the wire contract. Grep for the literal value across the codebase; these bugs hide in multiple call sites at once (here: 3 call sites + 1 validation whitelist, all wrong the same way, because they all trace back to one convention decision).

**3. Minor/SUGGESTION-level notes from the same review** (do not re-litigate as CRITICAL if seen again, already accepted tradeoffs):
- `DeliverTrackingEventJob::recordOutcome()` persists `client_ip`/`client_user_agent`/`fbp`/`fbc`/`gclid` UNHASHED (by design — Meta/Google need them raw) into `tracking_event.request_payload` (central table, no retention/pruning job defined). Low-severity privacy-hygiene note, not a hard violation — email/phone/external_id ARE correctly hashed before persistence via `TrackingEvent::hashedUserData()`.
- Theoretical duplicate-send risk: if `recordOutcome(STATUS_SENT)` throws AFTER a successful external POST, the `catch` in `handle()` treats it as a channel failure and retries → could re-POST to Facebook/GA4 an event that already succeeded. Facebook self-dedupes via `event_id` (the whole point of that field), GA4 Measurement Protocol does not — so a genuine double-count is only possible on the GA4 side, and only in the rare case of a DB write failing right after a successful HTTP call. Not worth blocking on, worth a one-line note only.

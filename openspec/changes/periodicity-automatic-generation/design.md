# Technical Design: Periodicity-Driven Automatic Charge Generation

> Scope: keep it SIMPLE and pragmatic (user: "simplementala") but resolve the load-bearing
> decisions. No new tables, no over-engineering. One ALTER per affected table, one small
> resolver class, one generalized command.

## 1. Architecture Approach

**Pattern:** Catalog-as-contract + a thin Strategy/Resolver for scheduling.

- The `periodicity` central catalog gains a single boolean column `is_automatic`. That column is the **single source of truth** for "this periodicity is generated by the cron", consumed identically by backend (filter) and frontend (badge/warning). No more hardcoded `MONTHLY` UUID comparisons on either side.
- The daily cron stops hardcoding `Periodicity::MONTHLY`. It iterates `Periodicity::where('is_automatic', true)` and, for each automatic periodicity, asks a **`PeriodicityScheduleResolver`** two questions for *today*: (a) "do you fire today for this tenant's `generation_day`?" and, if yes, (b) "what is the period identity (idempotency key) + `issued_at` + `due_date`?". The command itself stays the orchestrator (tenant loop, batch create/activate, treasurer summary); all per-type date math lives in the resolver.
- This keeps the SOLID boundary clean: the command knows *that* periodicities fire; the resolver knows *when/how*. Adding a future periodicity = one new branch in the resolver + one seeded row, with **zero** changes to the command body.

**Layering:**
```
Command (orchestration: tenant loop, create batch, activate, notify)
   └─ PeriodicityScheduleResolver (pure date logic: shouldRunToday + period descriptor)
         └─ returns PeriodRun[] (value objects: periodKey, year, month, cycle, issuedAt, dueDate, label)
   └─ ChargeGenerationService::activateBatch (UNCHANGED — already idempotent)
```

The resolver is **pure** (input: periodicity type, `Carbon $today`, `int $generationDay`; output: array of `PeriodRun` descriptors). Pure = trivially unit-testable, which matters most for the EoM/biweekly math.

## 4. Decision 3 — Scheduling abstraction (`PeriodicityScheduleResolver`)

New class: `Modules/Collections/app/Services/PeriodicityScheduleResolver.php`.

It returns an array of `PeriodRun` descriptors for a given periodicity *today* (array is empty when nothing fires today; usually 0 or 1 element, BIWEEKLY can return 1 on its two trigger days). Each `PeriodRun` carries everything the command needs to build a batch:

```php
final readonly class PeriodRun
{
    public function __construct(
        public int $year,
        public ?int $month,   // null only for non-period batches; here always set
        public ?int $cycle,   // discriminator within the month for weekly/biweekly; null for monthly/bimonthly/yearly
        public string $periodLabel, // human title fragment, e.g. "junio 2026", "semana del 9 jun 2026", "1ra quincena junio 2026"
        public Carbon $issuedAt,
        public Carbon $dueDate,
    ) {}
}
```

The resolver signature:
```php
/** @return PeriodRun[] */
public function runsForToday(string $periodicityId, Carbon $today, int $generationDay): array
```

### Per-periodicity rules (pragmatic, fixed conventions)

`$generationDay` is the tenant's `collections.charge_generation_day` (1–28, clamped — existing behavior). Default due date keeps the current convention `issued_at + 15 days` unless noted.

| Periodicity | Fires today when… | year | month | cycle | issued_at | due_date |
|-------------|-------------------|------|-------|-------|-----------|----------|
| **MONTHLY** | `today->day === generationDay` (clamped 1–28) | today.year | today.month | `null` | today | today + 15d |
| **BIMONTHLY** | `today->day === generationDay` **AND** `today.month` is odd (Jan, Mar, May, Jul, Sep, Nov) | today.year | today.month | `null` | today | today + 15d |
| **YEARLY** | `today->day === generationDay` **AND** `today.month === 1` (January) | today.year | today.month (=1) | `null` | today | today + 15d |
| **WEEKLY** | `today->dayOfWeekIso === 1` (Monday) — ignores `generationDay` | today.year | today.month | **ISO week number** `today->isoWeek` | today | today + 7d |
| **BIWEEKLY** | `today->day === 15` **OR** `today` is the last day of the month — ignores `generationDay` | today.year | today.month | **1** (mid-month, day 15) / **2** (end-of-month) | today | today + 15d |

**Rationale for the conventions (all deliberately simple, documented in code comments):**
- **BIMONTHLY = odd months.** Picking "odd months" gives a deterministic, stateless rule (no cursor table, no "every 2 months since concept creation"). Jan/Mar/May/Jul/Sep/Nov → 6 runs/year, evenly spaced. The proposal flagged this as a design call; odd-month is the simplest correct stateless choice.
- **YEARLY = January.** Once a year, on `generationDay` of January. Deterministic, no per-concept anchor needed.
- **WEEKLY = Monday.** A fixed weekday is the pragmatic choice — `generationDay` (a day-of-month) is meaningless for a weekly cadence, so weekly ignores it. Monday (`dayOfWeekIso === 1`) is the convention. Due date is `+7d` (one cycle), not `+15d`, because a weekly charge whose due date is longer than its period would overlap the next charge.
- **BIWEEKLY (Quincenal) = day 15 + last day of month.** Two runs per month. This is the only periodicity that can produce TWO distinct period identities in the same calendar month → it is the reason the idempotency key needs a discriminator (Decision 4). `generationDay` is ignored (a biweekly cadence is anchored to the 15th and EoM by convention, not to an arbitrary configurable day).

### End-of-Month (EoM) date math — explicit

The biweekly "last day of month" detection and clamp:
```php
// Detect "today is the last day of this month" — robust for 28/29/30/31.
$isLastDayOfMonth = $today->day === $today->copy()->endOfMonth()->day;

// BIWEEKLY trigger:
//   cycle 1 → day === 15
//   cycle 2 → isLastDayOfMonth (Feb 28/29, 30-day months: 30, 31-day months: 31)
```
- No "Feb 30" hazard: we never *target* a fixed day like 30/31; we ask Carbon for the month's actual last day via `endOfMonth()`. February (28 or 29 in a leap year) is handled automatically.
- The existing monthly path already clamps `generationDay` to 1–28 (`max(1, min(28, $generationDay))`) so monthly never misses a short month — that clamp stays for MONTHLY/BIMONTHLY/YEARLY. BIWEEKLY does NOT use `generationDay`, so it is unaffected by the clamp.
- WEEKLY uses `isoWeek` (1–53) as the cycle. ISO week is stable across month boundaries and gives a clean year+week identity. A week that straddles two months still produces one run on its Monday; we record `month = today.month` (the Monday's month) which, combined with `cycle = isoWeek`, is unambiguous.

### Why a resolver, not a `match` inline in the command
Putting the date math in a pure, injectable class:
1. lets us unit-test EoM/leap-year/odd-month edge cases without booting a tenant or touching the DB;
2. keeps the command's tenant loop readable (it just maps each `PeriodRun` to a `ChargeBatch::create` + `activateBatch`);
3. isolates the "future periodicity" extension point to one file.

## 5. Decision 4 — Idempotency: add a `cycle` discriminator

**Problem:** the current partial unique index
`charge_batch_monthly_unique (tenant_id, charge_concept_id, year, month) WHERE deleted_at IS NULL AND month IS NOT NULL`
treats one (concept, year, month) as unique. WEEKLY (multiple Mondays/month) and BIWEEKLY (two runs/month) would collide on the second run within a month and be silently skipped → only the first cycle ever generates. That is a correctness bug.

**Chosen option (simplest correct): add a nullable `cycle` smallint column + a new partial unique index that includes `cycle`; keep the monthly index working by making `cycle` NULL for monthly/bimonthly/yearly.**

Rejected alternatives:
- **Encode the cycle into `month`** (e.g. `month*100 + week`): pollutes the `month` column semantics that the rest of the system reads (`generateForNewUnit` filters `where('month', $now->month)`; UI shows month). Rejected — breaks existing readers.
- **A separate `period_key` string column** (e.g. `"2026-W24"`): works, but a free-form string is harder to index/validate and duplicates info already in `year`/`month`. A typed `smallint cycle` is leaner and composes with the existing `(year, month)` columns.
- **Hash-based key:** opaque, undebuggable. Rejected.

### Migration (new file, append-only)
`Modules/Collections/database/migrations/2026_06_13_000002_add_cycle_to_charge_batch_table.php`

```php
public function up(): void
{
    Schema::table('charge_batch', function (Blueprint $table) {
        $table->smallInteger('cycle')
            ->nullable()
            ->after('month')
            ->comment('Sub-period discriminator within a month for sub-monthly periodicities: WEEKLY=ISO week number, BIWEEKLY=1 (day 15)|2 (end of month). NULL for monthly/bimonthly/yearly/eventual.');
    });

    // Replace the monthly-only unique with one that also isolates by cycle.
    // Old index keyed (tenant_id, concept, year, month); two NULL-cycle monthly
    // batches in the same month would now (with cycle in the key) BOTH be allowed
    // because NULLs are distinct in a Postgres unique — so we must COALESCE cycle
    // to a sentinel to preserve the monthly guard. See note below.
    DB::statement('DROP INDEX IF EXISTS charge_batch_monthly_unique');
    DB::statement(
        'CREATE UNIQUE INDEX charge_batch_period_unique ON "charge_batch" '
        .'(tenant_id, charge_concept_id, year, month, COALESCE(cycle, -1)) '
        .'WHERE deleted_at IS NULL AND month IS NOT NULL'
    );
}

public function down(): void
{
    DB::statement('DROP INDEX IF EXISTS charge_batch_period_unique');
    DB::statement(
        'CREATE UNIQUE INDEX charge_batch_monthly_unique ON "charge_batch" '
        .'(tenant_id, charge_concept_id, year, month) '
        .'WHERE deleted_at IS NULL AND month IS NOT NULL'
    );
    Schema::table('charge_batch', function (Blueprint $table) {
        $table->dropColumn('cycle');
    });
}
```

**Critical correctness note — Postgres NULL in unique indexes:** in Postgres, two rows with `NULL` in a unique column are considered DISTINCT (NULLs don't equal each other). If we put bare `cycle` in the index, the monthly guard would BREAK (two monthly batches, both `cycle = NULL`, same month → both allowed = double-charge regression). The fix is `COALESCE(cycle, -1)` in the index expression: monthly rows collapse to the sentinel `-1` and collide as before; weekly/biweekly rows carry distinct cycle values and are correctly isolated. This is the load-bearing line of the whole idempotency change — it MUST be `COALESCE(cycle, -1)`, not bare `cycle`.

**Model** (`ChargeBatch.php`): add `'cycle'` to `$fillable` and cast `'cycle' => 'integer'`. (Implementer: verify the model's `$fillable`/`casts` — not shown here but follows the same pattern as `year`/`month`.)

**No regression on existing data:** existing monthly batches have `cycle = NULL` → `COALESCE(-1)` → identical behavior to the old index. The `WHERE month IS NOT NULL` clause is preserved, so eventual batches (month NULL) remain unconstrained exactly as before.

## 6. Decision 5 — Generalize the command

**Keep the artisan signature `collections:generate-monthly`.** Rationale: the scheduler entry in `CollectionsServiceProvider::registerCommandSchedules()` (line 68, `->dailyAt('06:00')`) references it, the proposal's "minimal disruption to the scheduler" principle, and tests likely call `collections:generate-monthly`. Renaming the signature would require touching the provider + any tests + ops runbooks for zero functional gain.

> Trade-off acknowledged: the name becomes a slight misnomer (it now generates more than monthly). Mitigation: update the class docblock + `$description` to say "recurring charges (all automatic periodicities)". If the team later wants a truthful name, add an alias `collections:generate-recurring` pointing at the same handler in a follow-up — out of scope here. The DESIGN decision is: **do not rename now.**

**Refactor `handle()`/`generateForTenant()`** (`GenerateMonthlyChargesCommand.php`):

1. Inject `PeriodicityScheduleResolver` alongside `ChargeGenerationService` in `handle()`.
2. Inside each tenant's `run()` callback, fetch the automatic periodicities ONCE:
   `$autoPeriodicities = Periodicity::where('is_automatic', true)->where('is_active', true)->get();`
   (central catalog — same rows for every tenant, but fetched inside the loop keeps it simple; or hoist outside the tenant loop since the catalog is tenant-independent — **hoist it**, it's central data, one query total.)
3. For each automatic periodicity, call `$resolver->runsForToday($periodicity->id, $today, $generationDay)`.
4. For each returned `PeriodRun`, find that periodicity's active+vigent concepts (reusing the EXACT existing vigencia query, just parameterized by `$periodicity->id` instead of the hardcoded monthly id) and create+activate one batch per concept, passing `year`, `month`, `cycle`, `issued_at`, `due_date`, and `title` (built from `concept->name` + `periodRun->periodLabel`).
5. The existing `UniqueConstraintViolationException` recovery block stays, but the "find existing" lookup MUST now also match `cycle`:
   ```php
   $existing = ChargeBatch::where('charge_concept_id', $concept->id)
       ->where('year', $run->year)
       ->where('month', $run->month)
       ->where('cycle', $run->cycle) // <-- new; NULL-safe via whereNull when cycle is null
       ->whereNull('deleted_at')
       ->first();
   ```
   Note: `where('cycle', null)` does NOT match NULL in SQL — use a conditional:
   `$run->cycle === null ? $q->whereNull('cycle') : $q->where('cycle', $run->cycle)`.
6. The treasurer summary (`notifyTreasurerSummary`) is unchanged — it already aggregates whatever batches were generated. The notification title "Cargos mensuales generados" should be softened to "Cargos generados" (cosmetic, since it can now include weekly/biweekly). Optional, low priority.

**Concept query parameterization** — extract the existing vigencia query into a small private helper `activeConceptsFor(string $periodicityId, Carbon $today)` so the same validity logic (valid_from <= today, valid_to null or >= today, is_active, not soft-deleted) is reused across all periodicities. This is a pure refactor of existing code, no behavior change for monthly.

**Idempotency carry-through:** `ChargeGenerationService::activateBatch` is UNCHANGED — it operates on a batch row and is already idempotent (lock + status re-check). The new `cycle` is just another column on the batch; the service doesn't need to know about it.

## 8. Data Flow (end to end)

```
Cron (daily 06:00, collections:generate-monthly)
  → for each Tenant: tenant->run():
      generationDay = Setting::getValue('collections.charge_generation_day') ?? 1
      autoPeriodicities = Periodicity::where(is_automatic, true)->where(is_active,true)->get()  [hoisted, central]
      for each periodicity:
        runs = PeriodicityScheduleResolver::runsForToday(periodicity.id, today, generationDay)  [0..1 runs]
        for each run (PeriodRun):
          concepts = activeConceptsFor(periodicity.id, today)   [reused vigencia query]
          for each concept:
            ChargeBatch::create({concept, year, month, cycle, issued_at, due_date, title, target=all, status=DRAFT})
              → on UniqueConstraintViolation (cycle-aware lookup): ensure existing batch active
            ChargeGenerationService::activateBatch(batch)   [UNCHANGED, idempotent]
      notifyTreasurerSummary(generatedBatches)

Frontend
  ChargeConcept payload (Orion include 'periodicity')  → concept.periodicity.is_automatic
  isAutoGenerated(concept) → badge (list) + warning (batch modal)   [no UUID hardcoding]
```

## 9. Integration Points & Contracts

| Boundary | Contract |
|----------|----------|
| Migration ↔ existing monthly cron | `cycle = NULL` + `COALESCE(cycle,-1)` index = byte-for-byte identical idempotency for monthly. No monthly regression. |
| Resolver ↔ command | `runsForToday()` returns `PeriodRun[]`; command maps each to a batch. Resolver is pure, DB-free. |
| Backend ↔ frontend | `periodicity.is_automatic` boolean on the `/selects` periodicity rows and on `concept.periodicity` (via `includes()`). Backend deploys FIRST (proposal dependency). |
| Catalog ↔ all tenants | Central `periodicity` ALTER + seeder = single global change; no per-tenant migration (single-DB tenancy). |

## 10. ADR Summary (decisions + rejected alternatives)

- **ADR-1: `is_automatic` boolean on central `periodicity`** (not a per-concept flag, not a hardcoded list). Rejected: per-concept schedule (out of scope, over-engineered); enum-of-types (project bans native enums — laravel-backend-architecture rule 14). Chosen for single-source-of-truth on both layers.
- **ADR-2: Pure `PeriodicityScheduleResolver` strategy** (not inline `match` in command, not a DB-backed cursor). Rejected: stateful cursor table for "every N months" (needs a table + anchor; the stateless odd-month rule is simpler and deterministic). Chosen for testability + extension isolation.
- **ADR-3: `cycle` smallint + `COALESCE(cycle,-1)` partial unique** (not month-encoding, not free-form `period_key`, not hash). Chosen as the leanest correct discriminator that preserves the monthly guard (the COALESCE handles Postgres NULL-distinctness).
- **ADR-4: Keep `collections:generate-monthly` signature** (no rename). Rejected: rename to `:generate-recurring` (touches scheduler + tests for no functional gain). Trade-off: name is a mild misnomer; documented in docblock.
- **ADR-5: Fixed scheduling conventions** — bimonthly=odd months, yearly=January, weekly=Monday, biweekly=15th+EoM. Chosen for stateless determinism over configurable-but-complex anchors. EoM via Carbon `endOfMonth()` (no Feb-30 hazard).
